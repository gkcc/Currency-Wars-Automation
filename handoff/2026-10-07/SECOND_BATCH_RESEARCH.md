# 后续修复采用的通用方法

本轮源码盘点基准为 `beaea343ee7edf29bcba70ba8351a7dc462a83da`。下列网页于 2026-10-07（Asia/Shanghai）实际打开；外部可变文档不作为本游戏实机成功证据。方法只补现有执行器的具体缺口，不安装第二输入控制器、工作流引擎或监控服务。

各项代码按独立提交交付，以对应 B 编号实施说明和 PR 的实际 SHA 为准；本研究说明不代表当前提交已经包含后续所有修改。

## 1. 恢复先对账已发生的动作，再判断当前目标

依据：[AWS 幂等请求实践](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)、[EC2 请求幂等性](https://docs.aws.amazon.com/ec2/latest/devguide/ec2-api-idempotency.html)、[LangGraph 函数接口的确定性与幂等性](https://docs.langchain.com/oss/python/langgraph/functional-api#idempotency)。

AWS 的做法是由调用方提供唯一请求身份，保存原参数，重复请求返回原结果；同一身份而参数不同应拒绝。LangGraph 文档也明确，已完成任务可以复用结果，但开始后未完成的副作用仍可能再次执行，需要幂等键或核既有结果。游戏点击本身没有服务端幂等保证，所以本项目只采用“持久结果、身份对账、未定副作用不盲重放”这一部分。

本项目已具备 request-ledger、手操检查点、CAS、epoch 和变更围栏，缺的是结果分级与恢复后的必要事实重验。实现应分别保留：

- 请求事实：是否发布、动作尝试、完成前缀、原请求与原结果；不能用 `completed=[]` 宣称从未发送输入。
- 业务效果：真实新帧中的成功、零效果、部分或未知；图像哈希变化不是业务成功。
- 阶段事实：哪些前置条件仍成立、哪些操作使其失效。恢复事件与旧/新 epoch 绑定，新的暂停和接管继续优先。

当前没有全场奖励领空的原生识别器。恢复时不能把历史 `all_claimed` 套上新截图当成刚完成重扫；应在当前请求接受一次真实监督领空复核，再继续检查其余可保留阶段。任务面板暂时缺节点时可以延后验证；错误身份、改写证据或未覆盖输入则明确拒绝。

本轮重新访问旧 `durable-execution` 地址时实际重定向到 [Persistence](https://docs.langchain.com/oss/python/langgraph/persistence)，不再按旧地址名称推定页面内容。所需“未完成副作用可能重跑”的明确说明来自上述函数接口页面。

## 2. 奖励与经济采用明确前置条件和实际效果

依据：[Unified Planning 问题表示](https://unified-planning.readthedocs.io/en/latest/problem_representation.html)。该官方文档解释动作的前置条件、效果及目标；项目已有 `progression_plan` 使用类似的目标缺口表达，继续复用。

本项目的具体设计来自用户已确认的业务要求：奖励领空、指南、无用牌清理、当前缺口、免费刷新、付费预算/停止条件先于经验。前置条件必须由当前实读支持，动作效果必须通过原收据和新帧验证；在计划中写“卖出后有空位”不等于已经出现空位。

| 问题 | 已有能力 | 本轮补充范围 |
| --- | --- | --- |
| 满席阻塞领奖 | 备战席九槽、准备阶段、原拖动和局部目标守卫 | 单次、当前请求绑定的必要腾位；保存实际发布请求，实际释放位置与金币回读后回领奖 |
| 库存与人口混淆 | 前四/后六/备战席九槽独立位置 | 备战席占用与临时溢出分别表达；8/8不能证库存未满，未观察到溢出行也不能假设溢出为零 |
| 经验抢占搜牌预算 | 实价/攻略/模式守卫及单次动作执行 | 明确当前缺口、免费次数、付费搜牌上限与停止原因、购买资金预留，再决定经验 |
| 计数被当成效果 | 唯一请求收据及输入后观察 | 经验、等级、金币、免费次数、商店和库存差额核实；部分或未知效果不重发整批 |
| 特权卡任务没有执行闭环 | 已实读任务缺口、资源机会、攻略排序 | 优先关联当前可得卡选项；没有完整资源/装备目标/控件证据时继续待实证，不把建议标成已执行 |

不添加通用规划求解器。50储备、末期放开、关键缺口与策略同场要求由统一预算表达；剩余结息回合不可靠时保持未知，不能从节点字符串猜最终战。

## 3. F键与等待条件各自需要正确的证据

依据：[Windows 虚拟键表](https://learn.microsoft.com/en-us/windows/win32/inputdev/virtual-key-codes)、[GetLastInputInfo](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getlastinputinfo)。

F 对应 `0x46`，即十进制70；游戏将该键绑定经验的证据来自本机 UI 标F及66→54金币、40/52→8级0/72的实际变化，不由通用键表推断。后续源码需同时统一准备/商店许可、经济分类、策略前置、实际效果及失效范围；大世界的F交互按页面保留原含义。

`GetLastInputInfo` 只给当前会话的最后输入时间，官方文档明确该时间值不保证逐次递增，注入输入也可能影响它。它不能单独证明某个所有者已经完成交接。这支持继续使用项目已有光标、按键、前台和CAS检查；不据此倒推出本机0–80ms的具体来源，也不归因旧worker退出。

B-008的额外500ms等待属于临时ROOT助手，本机已在恢复、点击、F三次、拖动和两次出战通过。当前核心没有增加这项等待，不再把它当作待修broker问题。

## 4. 人口读取优先复用现有数字区域

依据：[OpenCV 区域裁切](https://opencv.org/cropping-an-image-using-opencv/)，以及本项目实际安装的 `rapidocr-onnxruntime==1.4.4` 的 `use_det=False/use_cls=False` 调用能力。

金币与人口已有固定数字区域识别，无需换模型。当前人口代码的具体遗漏是：格式合法而数值不可能的18/8挡住局部补读，随后又被范围检查拒绝。本轮小修复使这种情况能触发原有数字区域读取；原文字/位置/置信度保留，不删除前缀、不按已知等级或人工数人数回填。

只有实际数字区域产生唯一合法高置信结果才可采用；多个可能成立的读数、低置信、缺锚点或不支持布局继续未知。原生军阵完整性、姓名星级和位置检查仍独立。尚缺本机原图，合成路径测试不等于真实OCR验收。
