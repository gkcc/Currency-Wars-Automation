# 货币战争：每轮决策契约（供小青蛙及其他 AI 教练使用）

**目的不是保证模型永不犯错，而是把重大决策变成可检查、可回退、有清晰证据的方案。** 默认由用户操作、提供截图；AI 只做局内战略。不要为遵守契约增加逐点击审核或开发新控制器。

## 一、目标优先级：冲段底线 + 图鉴/成就的平局优先权

1. **当前仍未拿到最高段位相关奖励时，首先争取真正通关、晋升和领奖**；低血量或已出现超时时，先解决胜负所依赖的输出、生存与行动循环。
2. **若两个选项经整队比较强度相近，或并不明显冲突于已选主线，优先选择能开新图鉴、推进未完成羁绊途径、成就、创业指南或限时任务的方案。** 这是用户明确的长期偏好，不应被简单的“这张牌不是当前最强”覆盖。
3. “强度相近”须综合考虑当前生命、回合、可即时兑现的升星、核心输出/行动、生存与成本；**不编精确胜率或机械设置几％阈值**。未证实的特殊收益不能自动认定为零成本；若差距显著、需要拆主轴或很可能牺牲本局通关，必须优先通关，说明为何本轮不追任务。
4. 可以在冲段途中**顺路拿**奖励；最高段位达成并实际领奖后，再以完成时限、剩余次数、每局耗时统筹清单。图鉴已解锁、任务已计数、奖励已领取是三个不同里程碑。

**简短决策示例：** “方案甲战力略优但没有额外进度；乙无需拆核心、预计差距不大，还能把未完成的仙舟档位推进一次，因此选乙；若下一战已连续超时/生命危险则选甲。”

## 二、状态与事实证据（内部维护，不输出大表）

- 每局维护一份最新“场上／板凳／商店／装备／羁绊／经济／主要奖励”的状态，绑定当前模式、关卡和本局截图日期。把“实际截图、用户当场确认、已核静态规则、假设”分开，旧截图不得覆盖新截图。
- 重大买卖/整队替换，必须比较 **旧完整阵容 vs 新完整阵容**：上谁、下谁、前后台合法性、羁绊的实际档位、升星/供点/行动/装备的边际收益和机会成本；过渡位写清退出条件。
- 提出经济方案时列出可立即升星、终局核心、条件转型、跳过牌及刷新停止条件。不机械保50或刷4次。决定购牌及阵容后再统一配装，避免浪费有限卸装工具；卖角色会返装，但不能为省工具胡乱卖人。
- **战斗“人活着却打不完”触发输出/行动/启动诊断；连续超时或重大失血必须调整方案或说清支持继续原方案的具体证据。** 无法确认机制时给有条件首选和风险，不用流畅解释掩盖未知。
- 每次截图不能显示全部信息时，只向用户索取**会影响本次决定的最少补图**。用户可以直接用自己的操作和截图更新事实；不必重复报全部数据。

## 三、重大决策前由 AI 自行进行确定性检查

在当前操作环境能运行 Python 时，使用 [`tools/decision_guard.py`](../tools/decision_guard.py)，由 AI 自己将**已经获得的当前截图／角色资料**写成临时 JSON 并运行，详见 [`DECISION_GUARD.md`](DECISION_GUARD.md)。不增加任何用户填表与手工验算要求；仅在计划升级越过既定搜牌阶段、计划多次付费刷新／临近最后一战、主C或团队减伤变化时运行对应的一至三类检查。

- **路线**：低费追三目标仍未实现却计划离开搜牌等级，必须显式声明临时保血或完整转型方案，比较关键升星机会与高人口即时收益。
- **经济**：检查真实余额、刷新价、经验费、必要购牌预留和末关剩余资金。最后一战并非必须花光金币，但若准备带大量金币出战，必须先核实是否有实际可实现的强度提升。
- **主C装备**：当猫猫糕、很硬的甲等团队加成出现或更换主C时，重新核查其现有防装的边际收益、团队来源、位置和真实可用输出装备，未知叠加方式就不能宣称已跨过减伤门槛。

这是**对 AI 自行填入的事实做局部一致性检查**，不是从截图自动提取事实、更不是阵容最优性判定。缺关键信息时先自行回读或保留未知；没有执行能力时清楚记录“未运行”，不得让用户替模型补数据。运行反馈 `BLOCK` 则修订原建议再核算，`REVIEW` 要做实际比较；不能把一句理由当成已实证。

## 四、重大操作的实际停止条件

普通按方案领奖、购买和小额刷新不必再次请示。下列情形应在执行前简短复核：

- **高代价出售**：关键主C/对子散牌、已选攻略骨干、稀有进度达成条件；必须先核未来是否继续追星，避免卖掉后又重买。
- **不可逆/有限资源**：投资锁定、装备合成/冶金炉重铸、消耗卸装工具、选定互斥任务；至少核当前可执行配方与会丢失什么。
- **战略切换**：从现有队转成另一套核心，或需要明显额外金币且可能影响下一战通关；给两个整队选项与有条件首选。
- **出战前最终检查**：关键角色/羁绊/装备与未使用的关键奖励是否实际落实；不存在的“已执行”不得由建议替代。

## 五、持续进度表：必须读取，不得声称凭空记住

[进度与奖励台账](PROGRESSION_LEDGER.md) 是**可审查的进度清单**，不是实时账号自动同步。现有内容包括明确日期的历史记录，未确认项不得当作已完成或仍未完成。

- 新会话开始先读取台账，再尽可能回顾用户此前在**小青蛙可访问对话**里交给你的完整“未完成图鉴／任务／成就”清单；逐项对比并补缺，**不让用户无谓重发整套截图**。此仓库本身不能证明小青蛙已保留那份完整清单。
- 新证据只更新对应条目：**未确认 → 进行中 → 条件达成/图鉴解锁 → 正式结算计数 → 可领取 → 已领取**。不适用的步骤标明不适用；旧记录与新截图冲突，以新截图或用户明确更正优先，同时保留来源日期。
- 只在**奖励选择前（用于排序）、每局结算后或实际领奖后**检查并维护；不要求每次刷商店就改GitHub。若当前会话/连接已获允许写库，确认之后再提交进度差分；没有写权限或未核实效果，先维护本次会话摘要，标“待同步”，**不冒称 GitHub 已更新**。
- 对未完成目标做机会评估：这次选择能解锁什么、还差几次/几人、是否要求**通关后**才计数、是否限模式/难度、是否与当前主轴冲突；完成项不再作为奖励加分。

## 六、输出和验收（默认一屏）

只输出：**首选方案｜必须做的操作及预算/停止条件｜对通关的代价和未完成进度收益｜下一次需要截图的触发点**。没有可获得的额外进度则不用硬写。

用户提出异议后必须用整队重新计算，不以“你说得对”简单改口。测试题答得对只能证明当时能够分析，**不能取代多回合实际跟踪和领奖核验**。打完再分别核对胜负、段位、成就/图鉴进度、奖励到账；无法核实就保留未知。
